数组为什么要单独 hack？

数组下标没法逐个 defineProperty。Vue2 重写了 push / pop / shift / splice 等 7 个方法：调用后手动 dep.notify()，新增元素再走一遍 observe。

三个经典缺陷（必答）

  • 新增属性不响应 → 要 Vue.set
  • 直接改数组下标 / length 不响应
  • 初始化递归遍历，深对象开销大，且与数据量成正比
一分钟讲法：

「Vue2 是事前拦截：数据一进来就递归遍历，用 defineProperty 给每个属性装上 get/set。组件渲染时读到哪个属性，就把渲染 Watcher 收集进那个属性的 Dep；之后改这个属性，set 里 notify，Watcher 进队列，nextTick 里批量更新。所以它的问题也很明确：后加的属性没装拦截器，就不响应。」

追问预警：「为什么用 defineProperty 不用 Proxy？」→ 当年要兼容 IE11，Proxy 无 polyfill。别只说“性能差”，要说到无法拦截新增属性与数组下标这个根因。

① track / trigger

② computed 脏检查

③ scheduler / 队列

组件更新不直接执行 effect，而是塞进 job 队列：按组件 id 排序（父先于子）、同一 job 去重、flush 在微任务里完成，避免重复渲染。

一分钟讲法（补齐上次缺的四件套）：

「Vue3 是运行时收集。Proxy 的 get 里调 track，把当前正在跑的 effect 按 target + key 存进 targetMap；set 里调 trigger 把对应的 effects 取出来。但组件 effect 不直接重跑，走 scheduler 进队列去重排序后批量 flush。computed 是带 scheduler 的懒 effect，脏标记实现缓存。ref 是另一条线：基本类型用对象包装 + get/set，对象则转 reactive。」

滚动时算三件事

start = floor(scrollTop / itemHeight)
end = start + ceil(视口高 / itemHeight) + buffer
offsetY = start × itemHeight → 窗口 translateY(offsetY)

为什么滚动条是对的？

内层放一个高度 = 总条数 × 行高的幽灵占位元素，滚动条按真实总高走；真正的内容层绝对定位，只画窗口那一段。

定高 vs 不定高

定高直接算。不定高：先预估高度渲染，量到真实高度后缓存进数组 + 前缀和/二分查找定位 start，并修正 scrollTop 防抖动。

点按钮：假装用户往下滚了 320px，看 start / end / offset 怎么变。
一分钟讲法：

「核心就一句：DOM 数量和数据量解耦。监听 scroll 算出 start/end，只渲染这个切片，上下各留一屏缓冲防白屏；占位层保证滚动条真实，transform 定位保证位置对得上。代价是 Ctrl+F 搜不到屏外内容、行高不定要做高度缓存，这些取舍要主动说。」

追问预警：「滚动太快白屏怎么办？」→ 缓冲区 + 滚动时先渲染占位骨架 + 用 rAF 节流 scroll 处理。「为什么不用分页？」→ 无限滚动体验连续，但 DOM 不回收就会越滚越卡，虚拟列表是无限滚动的性能解法。

降采样为什么要「保极值」？

简单抽稀会把尖峰抽掉，曲线看起来平了、数据却说谎。正确做法：按像素列分桶，每桶保留 min / max（和首尾），尖峰永远在；要更保形用 LTTB（最大三角形三桶算法）。

Worker 放在哪一步才对？

Worker 只适合把降采样计算搬离主线程，它不解决「点太多」本身。顺序是：先窗口取数 → 再降采样（量大才上 Worker）→ 最后 Canvas。先说 Worker 就是答偏。

一分钟讲法：

安全设计 · 三道线（这份代码的安全关键点）

  • 拦原型链逃逸：UNSAFE_PROP = { constructor, __proto__, prototype }，所有成员访问都走 getProp 先查这张黑名单。为什么这三个最危险：x.constructor.constructor('...')() 能顺着原型链拿到 Function 构造器，进而执行任意代码，等同于 RCE。
  • 不用 eval / new Function：模板来自运营配置与外部输入，一旦能进 Function 就等于把代码执行权交出去；同时很多运行环境（CSP、小程序沙箱、安全审计）直接禁用它。
  • GLOBALS 白名单：自由标识符只能落到白名单里，目前只放 Math，且用 Object.create(null) 起底、无副作用、无 I/O。模板要用新全局，必须显式加进白名单。
  • 空值与非法调用兜底：成员访问时对象为 null / undefined 直接抛 TypeError 并带属性名，方便定位是哪条表达式写错；调用的不是函数时返回 undefined 而不是让整页崩掉。

性能与取舍 · 编译一次，渲染多次

  • 收益：同一模板反复渲染时，只付闭包调用 + 拼装的钱，不再付 parse、switch 分发、深拷贝的钱。旧的 new Function 版本每次渲染都要深克隆 element 再改克隆体，这份实现用浅拷贝合并替代了它。
  • 代价一 · 首次编译成本：第一次遇到模板要付 parse + compile，冷启动或模板量极大时要考虑预编译或懒编译时机。
  • 代价二 · 内存：两级缓存都以多占内存换少算，靠 WeakMap 让元素缓存可回收，表达式 Map 则随模板集合大小增长，需要有上限意识。
  • 代价三 · 元素视为不可变（必须主动说）：编译结果按 element 对象缓存，调用方若在两次渲染之间改了 element，缓存不会感知、会拿到旧结果。旧实现因为每次深克隆，反而能吃到这种 mutation——这是一个明确的行为差异，不是 bug，是用不可变约定换性能。

失败与降级 · 宁可编译期大声失败，不要运行期悄悄算错

  • 不支持的节点 / 运算符：compileExpr 的 default 直接抛 Unsupported AST node type / operator，在编译期暴露，而不是渲染时静默给错值。
  • each 解构：processEach 用正则拆 alias in/of exp 与迭代器 (alias, index)。旧 new Function 路径支持 ({a, b}, i) in list 这类解构写法，但真实模板没人这么用；这份实现用 IDENTIFIER_RE 校验 alias，不是合法标识符就直接抛错——大声失败好过静默算错。
  • 保留的历史怪癖：无 expression 时取 value，但 falsy 的 value（0 / '' / false / null）会被转成空字符串 ''——这是刻意保留的旧行为，改它之前要先确认存量模板没有依赖。
  • children 展平过滤：show 为假返回 false、each 返回数组，最后由 flattenFilter 把嵌套数组展平并滤掉 falsy 子节点，handler 拿到的永远是干净的一维 children。

代码骨架 · 面试时能默写的四段（细节看展开）

① 对外入口 createParser：WeakMap 缓存 + 原型链 scope 
export function createParser(handler, debug) {
  const cache = new WeakMap(); // element 对象 -> 已编译渲染函数
  return function parse(element, data) {
    let root = cache.get(element);
    if (!root) {
      root = compileNode(element, handler, new Map()); // Map 是 exprCache
      cache.set(element, root);
    }
    // 原型链 scope：先查 data，再落 GLOBALS 白名单（只有 Math）
    const scope = Object.assign(Object.create(GLOBALS), data);
    return root(scope);
  };
}

讲法：公开契约和旧版完全一致，还是 (element, data) => T，替换的是内部实现——调用方无感，这也是敢重构的前提。

② compileExpr 核心：短路逻辑 + 成员调用的 this 绑定 
function compileExpr(ast) {
  switch (ast.type) {
    case 'Literal': { const v = ast.value; return () => v; }
    case 'Identifier': return scope => scope[ast.name];
    case 'LogicalExpression': // && / || 必须短路，不能两侧都先求值
      if (ast.operator === '&&') {
        const l = compileExpr(ast.left), r = compileExpr(ast.right);
        return scope => { const v = l(scope); return v ? r(scope) : v; };
      }
      // || 同理
    case 'MemberExpression': // 所有成员访问都过 getProp 查黑名单
      return scope => getProp(compileExpr(ast.object)(scope), ast.property.name);
    case 'CallExpression':
      // 方法调用 fn.apply(obj, args) 保住 this；普通函数调用 apply(null, args)
  }
}

两个最容易被深挖的点：&& / || 要返回操作数本身且短路，不能编译成布尔运算；成员方法调用必须把宿主对象绑回 this，否则 list.includes(x) 这类依赖 this 的方法会出错。

③ compileNode：show / each 包装 + 静态与动态分离 
function compileNode(element, handler, exprCache) {
  if (element.each != null) {
    const { exp, alias, index } = processEach(element.each); // 正则拆 alias in list
    const getList = expr(exp);                               // 走 exprCache
    const inner = compileNode(restWithoutEach, handler, exprCache);
    return scope => getList(scope).map((item, i) => {
      const child = Object.create(scope); // 子作用域：原型链继承外层
      child[alias] = item; if (index) child[index] = i;
      return inner(child);
    });
  }
  if (element.show != null) {
    const getShow = expr(element.show);
    const inner = compileNode(restWithoutShow, handler, exprCache);
    return scope => getShow(scope) ? inner(scope) : false; // 假 -> false，后续被过滤
  }
  // 普通节点：静态属性进 staticEl，':' 开头进 patch；渲染时 buildMerged 浅拷贝合并
}

设计要点：show / each 不是在渲染时用 if 判断一遍，而是编译期就把内层编译函数包一层——渲染路径里没有指令判断，只有函数调用。

④ 安全拦截 getProp：一行守住逃逸入口 
const UNSAFE_PROP = new Set(['constructor', '__proto__', 'prototype']);
function getProp(obj, key) {
  if (UNSAFE_PROP.has(key)) throw new Error('Forbidden property access: ' + key);
  return obj[key];
}

为什么只拦这三个就够堵住主逃逸链：从任意对象出发，能通向 Function 构造器的路都要经过 constructor，能改原型污染的路都要经过 __proto__ / prototype，把这三个口子封死，模板表达式就只能读数据、调白名单内的方法。

一分钟讲法（按这份代码讲，照这个顺序）：

「先说为什么不用 eval 和 new Function：模板是外部可配置的，等于把执行权交出去，而且 CSP 和小程序沙箱也禁。这份实现分三步：第一步 jsep 只做解析，把表达式字符串变成 AST，对象字面量和模板字符串靠插件补齐，jsep 本身不执行代码；第二步 compileExpr 把 AST 编译成闭包树，把按类型分发的成本付在编译期，渲染时只跑闭包；第三步 compileNode 把整棵元素树编译掉，静态属性和冒号动态属性分离，show 和 each 编成包装函数，each 用原型链子作用域挂循环变量。缓存分两级：表达式按字符串进 Map，元素按对象进 WeakMap。安全靠三条：成员访问统一过 getProp 拦 constructor / __proto__ / prototype，全局只给白名单里的 Math，不支持的语法在编译期直接抛错，不静默算错。」

深挖追问预警：「为什么不直接用 new Function？」→ 安全（模板可注入）、环境（CSP / 小程序沙箱禁用）、可缓存性（字符串拼函数难以按节点做编译缓存与拦截）。「闭包编译比直接遍历 AST 快在哪？」→ 遍历解释器每次求值都要对每个节点做类型分发，闭包把分发提前到编译期一次付清，渲染越高频差距越大。「缓存什么时候失效？」→ 元素缓存按对象身份，约定元素不可变，改模板就是换新对象、自然换新缓存；若调用方原地 mutation，缓存会过期——这是明确写出来的取舍。「原型链 scope 有什么坑？」→ 查标识符会一路往上找到 GLOBALS 和 Object.prototype，所以数据侧 key 命名要避开白名单名，子作用域的 alias 会遮蔽外层同名字段，这正是 each 想要的语义。「方法调用 this 怎么处理？」→ 成员调用用 fn.apply(obj, args) 把宿主绑回去，普通函数调用 apply(null, ...)，两者在编译期就按 callee 类型分开编译。

第一层 · 大模型本身：先说清边界，再谈方案

它到底在算什么？

给定上文，预测下一个 token 的概率分布，再逐个采样生成。所谓「理解」是统计意义上的语言建模，不是查数据库。所以它不知道自己不知道——没依据时也会按最像的说法编下去，这就是幻觉的根源，不是偶尔的 bug。

三个硬约束（选型必答）

  • 上下文窗口有限：塞进去的不只是问题，还有系统提示、历史、检索片段、工具结果，超了就截断或涨成本
  • 知识有截止且无私有数据：训练后发生的事、公司内网文档，它一概没有——这是 RAG 存在的理由
  • 不擅长精确计算与实时状态：价格、库存、订单状态必须查真实系统，不许让模型「算」或「记」

前端要懂的几个词

  • Token：计费与长度单位，中英文切分不同，别按字数估成本
  • Temperature：采样随机性，事实问答调低、创意生成调高
  • 结构化输出：要求按 JSON Schema 返回，再做校验，自由文本没法接进系统
  • 流式输出：逐 token 返回，前端靠 SSE 增量渲染（见 SSE 那节）

第四层 · 评测与安全：没这层，前面全是 demo

Eval 怎么做（别凭感觉说「变好了」）

  • 先攒一批有标准答案的问答集（真实问题 + 期望答案 + 应命中的文档），改任何一环都全量重跑

安全与护栏（幻觉防不住，只能收敛）

  • 防提示注入：用户输入和检索回来的文档都是「数据」不是「指令」，别直接拼进系统提示当命令执行；文档里的诱导语句要隔离
  • 敏感数据不进 Prompt：隐私、密钥、未脱敏的主体信息先脱敏或不送模型（和 AIDOD 主体加密存是同一条意识）
  • 工具最小权限：工具白名单、最大步数、失败重试上限，写操作一律先出方案、人确认再执行，且可回滚、可审计
  • 成本与延迟：小模型做分类/改写、大模型做生成；高频问题缓存答案；别拿最贵的模型跑所有请求

落到前端 · 你能讲的三类活（别贪多，讲透一类即可）

① AI Coding 工作流

你用 Codex 的那套：意图先写成文档、Plan 拆步骤、Skill 沉淀团队规则、多 Agent 做 Code Review、历史修复沉淀成规则。资深的考点是全局把控——拆解、校验、兜底，而不是会调哪个工具。

② 产品里的 AI 功能

搜索、推荐、生成、体检类功能本质都是 RAG 或 Agent 的壳。前端难点不在调接口，在流式渲染（见 SSE 节）和状态同步：生成式 UI 要能中断、能重试、能在人确认后才落真实操作。

③ AIDOD 那条链（守住口径）

AIDOD 的知识库是指纹精确匹配，不是向量 RAG：指纹哈希精确查、规则 + 关键词召回，向量只做置信度打分那一侧的事。面试官问 RAG 别拿 AIDOD 顶，问 AIDOD 也别说成 RAG——两套是不同的召回思路，混了就是没分清。详见 AIDOD 那节。

一分钟讲法 · RAG 版（直接背）：

「知识天天变就别微调，先检索再生成。离线把文档按语义切块、向量化建库；在线用向量 + BM25 混合检索宽召回，再重排筛到 3–5 块拼进 Prompt，要求只依据片段作答、带出处，捞不到就说不知道。答不准先查切块、再查检索、最后查生成。」

一分钟讲法 · Agent 版（直接背）：

「Agent 是想、调工具、看结果的循环，模型只做决策，工具做真活。Skill 管怎么做，MCP 管够不着的系统，写操作人确认、可回滚。MCP Server 我没落地写过，只用过 Figma 和 Confluence 的；让我设计，就按模板库、预览渲染、线上观测这三个 Skill 够不着的缺口讲。」

追问预警：「切块大小怎么定？」→ 没有万能值，按文档类型试：手册类偏大保完整、问答类偏小保精准，用 Eval 集量出来，别报一个数字装懂。「向量库怎么选？」→ 先看量级与现有栈：量小直接用现有数据库的向量能力，量大再上专用库，选型服从运维成本，别为简历堆组件。「RAG 和长上下文谁更好？」→ 长上下文省了检索但贵且慢、还稀释注意力，知识量大、要更新、要出处时 RAG 仍是正解，两者可以叠：检索先筛，长上下文兜底读全篇。

Agent 上下文管理与记忆：模型本身无记忆，记忆是工程外挂

口径先定：这一节按原理与设计讲，不冒充落地过完整的记忆系统。一句话：LLM 是无状态的，每次调用都是一张白纸——所谓「Agent 有记忆」，全是外面的工程在每次调用前把该记的东西重新塞进上下文，调用后把该存的结论再写回库里。

短期记忆 · 上下文窗口就这么大，长任务靠三招续命

① 截断：最笨但必须有

窗口满了先丢最老的：早期闲聊、已完成的中间步骤先出局，系统提示和最近几轮永远保留。截断要有策略地丢，不能从中间乱切把一问一答切散。代价也直说：丢掉的细节模型就真忘了，所以重要结论不能只活在历史里。

② 摘要压缩：把历史压成小抄

把已走完的一大段对话 / 工具结果压成一段摘要（目标是什么、试过什么、结论是什么），用摘要替换原文继续往下跑。压缩本身也花一次模型调用，所以要攒够一段再压，别每轮都压；压的时候只留事实和结论，寒暄和试错过程全扔。

③ 结构化状态表：关键状态不靠「聊出来」

任务进度、已确认参数、待办清单维护成一张结构化状态（如 JSON / 表格）放在上下文固定位置，每步更新它。这样哪怕历史被截断、被压缩，模型低头看状态表就知道干到哪了——长任务不跑偏靠的是它，不是靠模型记性好。

长期记忆 · 分三类存，别混成一锅

事实记忆 · 关于用户和世界

稳定的事实与偏好：用户是谁、项目用什么栈、某个口径已经拍板。特点是条目化、可增删改，一条一个事实，变了就改那一条。

情节记忆 · 发生过什么事

带时间的事件与结论：上次那个问题最后怎么定的、某次任务做到哪一步、踩过什么坑。查的时候时效性权重高，旧情节要让位给新情节。

做法记忆 · 应该怎么做

流程、规范、检查清单——落到实物就是 Skill、系统提示、AGENTS.md 这类文件。它不按条取回，而是整份作为规则常驻：每次干活前先加载，管的是「做法」不是「事实」。

写入纪律：只写验证过的结论

  • 模型自己猜的、还没确认的，不许写进长期记忆——错记忆比没记忆更贵，它会在以后每次被捞出来误导
  • 用户改口、结论被推翻时，要作废旧条目（标记失效或删除），不能只追加新的一条让新旧并存打架
  • 每条记忆带上来源和时间，日后冲突时才分得清谁新谁旧、谁更可信

取回纪律：按三性排序，只取 3–5 条

  • 相关性：和当前任务语义最贴的优先（可以走向量检索，但捞的是记忆条目不是文档）
  • 时效性：同类事实取最新的，过期条目降权
  • 重要性：拍板过的口径、用户明确强调的偏好，权重压过随口提的一句
  • 只塞 3–5 条：塞多了稀释注意力、抬成本，还容易让旧记忆盖过当前指令

多 Agent 时：各自只拿自己那份上下文

多个 Agent 协作不是把全部历史广播给所有人：每个 Agent 只拿它这一步需要的切片——自己的任务说明、上游的结构化产出、和它相关的那几条记忆。这样做有三个好处：上下文不爆、互不污染（别的 Agent 的试错不会带偏它）、出了问题能定位是哪一份上下文给错了。共享的东西走结构化状态和长期记忆，不靠共享聊天记录。

续跑 · 用 AIDOD 的例子分清两个 ID（细节在 AIDOD 与 SSE 两节，这里只做交叉引用）

ID它是谁的管什么
thread_idCodex 那边的会话 ID管续跑：分析中断后，拿它回到同一个会话接着跑，模型还记得前面分析到哪——这是「任务级记忆」

顺带记死：流式中间内容不进库

分析边跑边产出的中间内容只放内存 / Redis 缓冲，跑完拼成文件存对象存储，DB 只存 thread_id、storage_key 和状态等元数据。所以「断了从库里重放内容」这个说法是错的：内容靠快照 + thread_id 续跑找回，不靠数据库。这正是短期记忆「不落库、用完即弃」在真实系统里的样子。

深拷贝 & 设计模式：一页速记

深拷贝的四个层次

  • JSON.parse(JSON.stringify())：丢函数/undefined/Symbol，循环引用直接报错，Date 变字符串
  • 递归手写版（面试标准答）：WeakMap 存已拷贝对象破循环引用；区分数组/对象/Date/RegExp/函数直接返回
  • structuredClone()：原生支持循环引用与多数内置类型，不能拷函数
  • 答题顺序：先说 JSON 法的三个坑 → 再写 WeakMap 递归版 → 最后提原生方案

设计模式只记前端真用得上的

  • 观察者 / 发布订阅：Vue 的 Dep-Watcher 就是观察者；EventBus 是发布订阅（多了中间人）— 两者区别必问
  • 策略模式：用映射表消灭 if-else 森林（如多币种格式化、多状态渲染）
  • 单例：全局 Store、请求缓存、弹窗管理器
  • 工厂 / 适配器：DSL 节点按 type 造组件 = 工厂；老接口包一层 = 适配器

每个模式都要能落回你自己的项目例子，背定义没用。逐个模式的完整例子、代码片段和误用警告看下一节 设计模式实例图鉴。

rem / 移动端适配一句话

rem 相对根字号：按设计稿宽度动态设 html font-size = 视口宽 / 10，元素尺寸写 rem 即可等比缩放；如今更常用 vw / 响应式断点，rem 的坑是字体不该跟着缩放、以及 DPR 与 1px 边框问题。被问到先讲原理，再讲「现在我会优先 vw + clamp」。

基础补漏 · 15B · 从背定义改成举例子 ★

设计模式实例图鉴：每个模式都落到你自己的代码上

选例原则：只收能对回你手里真实代码的模式，不凑 GoF 名录。每个模式按同一格式讲：解决什么问题 → 你的代码里在哪 → 最小片段 → 追问与误用。面试官问设计模式，考的从来不是定义默写，是你能不能先说清「当时有什么痛」，再说模式名。

1 · 适配器 Adapter —— 同一份 DSL，不同端各包一层 handler

解决什么：同一份数据结构，要喂给接口不一致的多个消费方，不想为每个消费方改数据源。

在哪：表达式引擎的 createParser(handler) 就是这个形状：DSL 和求值逻辑只写一份，handler(element, data, children) 由接入方实现——Web 侧 handler 把节点转成 Web 组件，RN 侧 handler 转成 RN 组件，解析器对端无感知。另一个日常例子是货币 / 日期格式化：业务只调统一的 formatCurrency(amount, country)，内部按国家配置表适配到底层格式化实现，业务不关心每个国家符号位置和精度怎么来的。

// 解析器不变，换 handler 就换一端
const parseWeb = createParser((el, data, kids) => renderWebNode(el, data, kids));
const parseRN  = createParser((el, data, kids) => renderRNNode(el, data, kids));

误用警告：适配层只做接口转换，不该在里面藏业务逻辑；适配的接口每变一次所有适配器都要跟着改，接口不稳定时先稳接口再谈适配。

2 · 策略 Strategy —— 用配置表 / 映射表消灭 if-else 森林

解决什么：同一件事有多种算法或规则，按条件选一种，且规则还会持续增加，if-else 每加一条就要改老代码。

在哪：三处现成的。一是 compileExpr 按 node.type 分发到各节点的编译策略，新增节点类型是加一个 case，不是改求值主流程；二是货币格式化按「国家 + 币种」查硬编码配置表（符号、精度、分隔符、compact 分表），加新国家是加一行配置，不是加一段分支；三是 AIDOD 置信度打分按规则明细逐项加分（代码命中多少分、日志命中多少分），规则可增减、明细可审计。

// 不是 if (country === 'ID') {...} else if ...
const rule = CURRENCY_RULES[country]; // { symbol, digits, position, separator }
return formatByRule(amount, rule);

追问预警：「策略和状态模式区别？」→ 策略是调用方主动选算法，状态是对象内部状态变了行为自动变，上下文感知不同。规则只有两三种且不会再长时，直接 if-else 更清楚，硬套映射表反而难读。

3 · 观察者 vs 发布订阅 —— 必考对照，别答混

解决什么：状态变了要通知一串依赖方，依赖方还要能动态增减。

在哪：Vue 的 Dep / Watcher 是观察者：每个属性的 Dep 直接持有它的 Watcher 列表，set 时直接 notify，没有中间人。EventBus、以及 SSE 那节的事件分发是发布订阅：发布者只把事件丢给事件中心，订阅者向中心登记，双方互不知道对方是谁。

观察者发布订阅
中间人无，主题直连观察者有，事件中心做中介
耦合主题知道观察者列表发布与订阅互不知情
你的例子Vue Dep → Watcher、Vue3 的 effect 依赖收集EventBus、SSE 事件按类型分发、组件间跨层通信
代价主题膨胀时通知链难追踪多一层调试成本，事件满天飞时难定位来源

讲法：一句话区分——「有没有中间人」。被问项目里用哪个，先说场景再报模式，不要两个都报显得都懂其实都没用过。

4 · 工厂 Factory —— 按 type 造对象，调用方不写 new 的细节

解决什么：对象种类多、创建逻辑分散时，把「按类型决定造哪个」收口到一处，新增类型只改工厂。

在哪：DSL 渲染时按节点 type 找对应组件来创建，就是工厂形状：模板只写 type 字符串，渲染器查映射表拿到组件并实例化，模板作者不需要知道组件怎么构造。另一处是 compileExpr 的编译分发：按 AST 节点类型「生产」出对应的求值闭包，调用方只拿到一个可调用的 EvalFn，不知道它内部是哪类节点的逻辑。jsep 插件的注册（jsep.plugins.register(objectPlugin, templatePlugin)）是配套的注册表思想：能力靠注册扩展，不改解析器本体。

const COMP = { banner: Banner, goodsList: GoodsList, coupon: Coupon };
function renderNode(node, data) {
  const C = COMP[node.type];
  return C ? C({ ...node.props, data }) : renderFallback(node); // 未知 type 要兜底
}

误用警告：工厂最容易漏的是未知类型的兜底——DSL 里出现没注册的 type 必须降级渲染或跳过并上报，不能直接抛错让整页白屏。

5 · 单例 Singleton —— 全局只该有一份的东西

解决什么：某些资源全局共享且只能有一份实例，重复创建会状态打架或纯浪费。

在哪：可以这样举例：解析器侧的表达式缓存随 parser 实例走，一个页面只建一个 parser、缓存全局复用；全局 Store（登录态、主题）、请求缓存层也是同理。前端多数单例不是用类写的，就是模块级变量——ES Module 本身只执行一次，导出的对象天然单例。

// 模块即单例：import 到哪都是同一份
let parser;
export function getParser(handler) {
  if (!parser) parser = createParser(handler);
  return parser;
}

追问与红线：单例最大的坑是把请求级状态放进全局单例——SSR 场景下多请求共用一个 Node 进程，全局变量存 locale 或用户信息就会串话，这正是国际化那节「语言进请求级上下文、绝不放全局变量」的教训。单例只适合放无状态或全局一致的东西。

6 · 模板方法 / 管线 Pipeline —— 骨架固定，步骤可换

解决什么：一类流程步骤顺序固定、但每步实现会变，需要保证顺序和兜底不被各实现方改乱。

在哪：两条现成的链。一是 Figma 转 DSL 的生产链：读节点 → 清洗 → 布局转换 → 组件映射 → 补字段 → 存库 → 校验回归，顺序是骨架，每步的规则可以持续增补，失败 case 归类成新规则补回对应步骤。二是 AIDOD 定位链：建任务 → 收上下文 → 定代码范围 → 查日志 → 指纹查知识库 → 分析 → 打分 → 人批，每步可单独重跑或替换，整条链的顺序和审计点位不变。compileNode 处理 each / show 再落到普通节点的固定顺序，也是一条小管线。

const PIPELINE = [readNodes, cleanNodes, convertLayout, mapComponents, fillFields, validate];
let dsl = raw;
for (const step of PIPELINE) dsl = step(dsl); // 顺序固定，单步可换实现、可单独测

误用警告：步骤之间只传数据、不互相直调，否则就退化成一团面条；每步要有明确的输入输出，某步挂了能定位到步、能从该步重跑。

7 · 解释器 Interpreter —— 表达式引擎本身就是它

解决什么：有一类可配置的小语言（不是图灵完备的业务代码），需要能存进配置、能校验、能安全执行。

在哪：就是上一节的表达式引擎：DSL 里的条件、绑定、样式表达式构成一个受限小语言，jsep 给出文法解析、AST 是它的句法结构、compileExpr 编译出的闭包是它的解释执行。为什么不用宿主语言直接写：配置要存库、要跨端、要过安全审计，宿主语言的 eval 三条都不满足，受限小语言牺牲表达能力换可控性，这正是 DSL 边界那节讲的取舍。

追问预警：「解释器模式和编译器有什么区别？」→ 面试语境下抓住一点：这里的目标是安全可控地求值，不是生成目标代码；这份实现进一步把解释做成「编译成闭包」，是解释器的一种优化实现。细节回 表达式引擎全流程 那节展开讲。

8 · 代理 / 装饰器（加分项）—— 不改原函数，给它加一层

解决什么：想给已有能力加缓存、重试、鉴权刷新、响应式追踪，又不想改它本体。

在哪：Vue3 的响应式就是语言级 Proxy：代理对象拦截 get / set 做依赖收集与触发，原对象一行不改。请求层是装饰器形状：把原始请求函数包一层，统一加 401 刷新后重试、错误码归一、请求去重，原函数只管发请求。两者共同点：增强发生在被包的那一层外面，被包者无感知。

async function withRefresh(requestFn) {
  try { return await requestFn(); }
  catch (e) { if (is401(e)) { await refreshTokenOnce(); return requestFn(); } throw e; }
}

误用警告：包装层数多了调用栈难追、出错难定位；Proxy 有性能成本且拦不住所有操作（如 in、自有属性枚举要单独处理），别把它讲成无代价的魔法。

HTTP / 缓存 / 跨域：一套图讲完

一句话：HTTP 解决「怎么传」，缓存解决「能不能不传」，跨域解决「浏览器同源策略下怎么安全地传」。

版本演进只记差异

  • 1.1：队头阻塞，一页开多连接凑数
  • HTTP/2：多路复用 + 头部压缩，一条连接并行跑
  • HTTP/3：QUIC/UDP，弱网丢包不拖住整条连接

HTTPS = HTTP + TLS

握手做两件事：用非对称加密协商出对称密钥（证书验身份），之后用对称加密传数据（快）。所以 HTTPS 防的是窃听和篡改，不防自己代码里的 XSS。

状态码按段记

2xx 成功 · 304 用缓存 · 4xx 客户端问题（401 未登录、403 无权限、404、429 限流）· 5xx 服务端问题。别把 401 和 403 说反。

跨域 CORS 到底卡在哪？

跨域是浏览器的同源策略，不是服务器拒绝。简单请求直接发、读响应时被拦；非简单请求先发 OPTIONS 预检，服务器回 Access-Control-Allow-* 才放行。解法优先级：后端配 CORS > 同源代理（开发时 Vite proxy / 生产 Nginx 反代）> JSONP（已淘汰，只作历史提一句）。带 Cookie 时还要 credentials + 明确 origin，不能用 *。

一分钟讲法：

「静态资源用内容 hash 文件名 + 强缓存长 max-age，HTML 用协商缓存保证能及时更新——这是我做发布时的默认策略。跨域我先分清是预检失败还是响应头没配，再决定改后端 CORS 还是走网关反代，不上来就说‘加个代理’。」

安全 · 19

XSS / CSRF + 登录鉴权：攻击怎么发生，防在哪层

XSS：把脚本注入页面

存储型（评论入库，别人打开中招）· 反射型（参数回显）· DOM 型（前端拼 innerHTML）。

防：输出编码/框架默认转义、富文本用白名单净化（如 DOMPurify）、CSP 兜底、Cookie 设 HttpOnly 让脚本偷不到。

CSRF：借你的登录态发请求

你在银行已登录，恶意站点自动提交一个表单，浏览器自动带上 Cookie 就成了。

防：SameSite Cookie、CSRF Token、校验 Origin/Referer、重要操作二次确认。关键区分：CSRF 利用的是「自动带凭证」，和 XSS 注入脚本是两回事。

登录鉴权三方案对比

方案凭证放哪 · 谁存状态取舍
Session + Cookie浏览器只存 sessionId，状态在服务端可主动踢人；多实例要共享 Session（如放 Redis）
JWTtoken 自带签名信息，服务端无状态校验易扩展；难主动失效，所以 access 短过期 + refresh 续期
OAuth 2.0第三方授权，拿授权码换 token解决「用微信/GitHub 登录」，不是登录协议本身
JWT 结构：Header.Payload.Signature — Payload 只是 Base64 编码不是加密，别往里放敏感信息。
一分钟讲法（接你练过的 token 刷新）：

「access token 短命，refresh token 长命放 HttpOnly Cookie。请求遇 401 时只刷一次、并发请求共用同一个刷新 Promise，刷完用新 token 重试原请求；刷新也失败才去登录。转账这类请求重试时还要复用同一幂等键，不能当新请求重发。」

诚实边界：鉴权细节问深了（签名算法、网关验签）就说「这块后端主导，我负责前端的存储、刷新和失效处理，联调时对齐的是过期策略和错误码」——划清边界比硬编强。
CSS · 20

CSS 布局速记：盒模型、BFC、Flex / Grid

盒模型 + box-sizing

标准模型 width 只算 content；box-sizing: border-box 后 width 含 padding + border，布局可预测，全局默认设它。margin 塌陷：相邻块级元素上下 margin 会合并取大值。

BFC 是什么、解决什么

一块独立渲染区域，内外互不影响。触发：overflow:hidden、浮动、绝对定位、display: flow-root（最干净）。用途：清浮动、阻止 margin 塌陷、自适应两栏。

Flex vs Grid 怎么选

  • Flex 一维：一行/一列内的对齐与分配（导航、工具栏）
  • Grid 二维：行列同时控制（卡片墙、仪表盘）
  • 口诀：内容决定布局用 Flex，布局决定内容用 Grid

居中四法（被问烂了）

  • Flex：display:flex; align-items:center; justify-content:center
  • Grid：place-items:center
  • 绝对定位 + transform: translate(-50%,-50%)
  • 文本：text-align + line-height（单行）

定位与层叠一句话

relative 占位偏移 · absolute 脱流找最近定位祖先 · fixed 相对视口 · sticky 滚动到阈值才粘。z-index 只在同一层叠上下文里比，先比上下文、再比 z-index，别无脑堆 9999。

讲法：

CSS 题别背属性表，每个概念配一个「它解决什么问题」：BFC 解决浮动和塌陷、border-box 解决宽度计算、Grid 解决二维布局。面试官要的是你写页面时真踩过，不是默写文档。

动态 import() 按路由拆、第三方库单独 vendor chunk、公共模块抽取。目标：首屏只下首屏的，和缓存策略配合（hash 文件名）。

Babel 做什么

语法转译（新语法→旧语法）+ 按 targets 注入 polyfill。它只管语法，不管打包；别和 Webpack 的职责说混。

对象结构优先 interface（可声明合并、表达继承直观）；联合、映射、工具类型用 type。日常区别不大，被追问就答「团队约定统一即可，我一般对象用 interface、组合类型用 type」。

  • any 关掉检查，能逃生不能常驻
  • unknown 安全版 any，用前必须收窄
  • 泛型 = 把类型当参数传，保住「输入输出同类型」的约束，如请求封装 get<T>()

数据库：索引、事务与表设计（前端要懂的那部分）

索引为什么快：B+ 树

索引是一棵按字段排序的 B+ 树，查一条从全表扫描变树上定位。代价：占空间、写时要维护索引，所以不是越多越好。联合索引讲清最左前缀：(a,b) 能帮只查 a 的，帮不了只查 b 的。

事务 ACID 一句话版

  • 原子性：要么全成要么全回滚（转账两步绑一起）
  • 一致性：前后数据守恒、约束不破
  • 隔离性：并发事务互不干扰，靠隔离级别 + 锁
  • 持久性：提交了断电也不丢

慢查询怎么排查

看执行计划 EXPLAIN：是否走索引、扫了多少行、是否文件排序。再对症：加/改索引、改写 SQL、分页别深 offset、避免 SELECT *。前端侧对应动作：列表接口只取需要的字段和页大小。

表设计（用你 AI DOD 的口径）

主表只放流转字段，上下文、主体、证据分表存；一对多别塞主表，大文本/文件只存元数据 + 存储 key。这套「瘦主表 + 分表」的讲法你已经纠正过两轮，直接复用。

MySQL vs Redis vs 向量库，别混着答

MySQL 存要事务、要关系查询的业务数据；Redis 存可丢、可重建的热点缓存与临时状态；向量库存 embedding 做相似检索（RAG 那节）。被问「为什么不全放 Redis」→ 持久性、事务和复杂查询它都不擅长。

一分钟讲法：

「我对数据库的要求是能参与表设计评审和慢接口联调：字段该不该进主表、列表查询走不走索引、分页方式选哪种，我能提出前端视角的意见；执行计划调优和锁的细节是后端主导，我讲到理解层为止。」——这个定位对前端岗是加分，对全栈岗也诚实。

缓存三大问题、消息队列与实时通信

问题发生什么解法
缓存穿透查根本不存在的 key，每次都打到 DB空值也缓存（短过期）/ 布隆过滤器先拦

缓存一致性怎么答

主流是 Cache Aside：读先查缓存、写先更新 DB 再删缓存（不是改缓存）。强一致做不到，目标是最终一致 + 可接受的短暂旧数据；对价格、余额这类强敏感数据干脆不缓存或极短过期——呼应你 SSR 那节「动态数据不进整页缓存」。

消息队列（MQ）三个用途

  • 异步：下单后发券/通知，不阻塞主流程
  • 削峰：秒杀流量先入队，慢慢消费
  • 解耦：生产者只管发，消费者增减互不影响

代价必提：消息可能重复（消费端也要幂等）、可能乱序、要处理积压和死信。

实时方案机制选型
轮询 / 长轮询客户端定时问 / 服务端 hold 住再回低频、实现最简；费请求
SSE服务端单向推，基于 HTTP通知、AI 流式输出（你 DOD 的流式推送就是这个思路）
WebSocket全双工长连接聊天、协同、行情等双向高频
一分钟讲法：

「缓存题我按穿透、击穿、雪崩三个词展开，每个都是‘请求绕过缓存打 DB’的不同姿势，解法都是在入口拦、在回源收口。实时通信按方向选：只需服务端推用 SSE，双向高频才上 WebSocket，别默认什么都 WebSocket。」

策略什么时候用为什么不用别的翻车 / 验证
SSG 静态构建时就能定：文档、营销页、发布才变的页不用 SSR：请求期没变量，提前渲染最快最便宜，还能整页上 CDN内容改了页面不变 → 忘了它只在构建时生成；验证看构建输出的 ○ 标记
ISR 增量静态内容会变但能容忍秒/分钟级旧数据：商品、店铺页不用纯 SSR：每请求都渲染，成本和 TTFB 都高；ISR 是「静态的速度 + 定时/按需再生」再生窗口内是旧数据，价格库存这类强实时数据不能放进来；用 revalidate / 按标签失效，验证看响应头缓存状态
SSR 动态每请求都不同：登录态、个性化、实时数据 + 要 SEO/首屏不用 CSR：首屏和 SEO 等不起 JS；不用 SSG：数据因人而异没法预渲染TTFB 被最慢的那个接口拖住 → 流式 + Suspense 先出壳；验证按 LCP 四段拆，别只看总时长
CSR 客户端登录后后台、强交互无 SEO 需求的页不用 SSR：服务端渲染纯属浪费，还多一层注水不一致风险首屏白屏时间长是预期内的，讲清这是主动取舍不是没优化

App Router 的核心机制：RSC 边界

Server Component 在服务端跑：不进浏览器 bundle、能直连数据库/内网接口、不能用 hooks 和浏览器 API；Client Component 用 'use client' 标记，边界以下才下发 JS。约束必须说清：跨边界传的 props 必须可序列化（函数、类实例传不过去）；'use client' 会向下传染，一个根组件标错，整棵子树的 JS 都进包——这是 bundle 莫名变大的头号原因。

缓存有四层，答错层就全错

  • 请求记忆化：同一次渲染内相同请求去重
  • Data Cache：服务端跨请求缓存取数结果，靠 revalidate / tag 失效
  • 整路由缓存：静态路由的 HTML + Payload 直接存
  • 客户端 Router Cache：切页时先用缓存的 Payload，短时间内不回源

「改了数据页面没变」先问是哪一层没失效，再动手；各版本默认缓存行为有变（如 fetch 默认缓存策略调整过），答的时候以目标版本文档为准，别把某个版本的默认值背成永恒真理。

为什么选 Next，为什么不选

选：React 团队要 SEO + 首屏、页面渲染策略混合（一个站里静态/动态/后台都有），约定换掉了自建 SSR 的取数、路由、缓存、失效四套基建。不选：纯后台系统（CSR 就够，上 Next 是负担）；已有成熟自研 SSR 体系且跑得稳（如你 Company 那套 render 入口）——迁移成本真实存在，Pages → App Router 就是一次大迁移，收益要算得过账。

怎么证明优化有效

  • 构建输出先看：每个路由是 ○ 静态还是 ƒ 动态、首屏 JS 多大——策略选没选对，构建时就见分晓
  • 线上按 LCP 四段拆（和第 06 节同一套方法）：TTFB 没降说明渲染策略没选对，光压缩资源没用
  • 注水错误、缓存命中看监控与响应头，不靠「感觉变快了」

  • 服务端用了 window/document → 报错，要放 onMounted 或判客户端

  • 注水不匹配：服务端/客户端分支渲染不同（如按时间、随机数）
  • 以为开了 SWR 就实时：再生窗口内仍是旧数据，强实时数据不能放

那货币包为什么不用 Intl、要手搓？（按这个顺序答）

先说口径：那个货币包是 Company Web FE Platform Team 的，你是使用者，手头只有 dist 和类型定义、没有源码，平台内部是否用 Intl 未证实，你讲的是「业务层为什么看不到 Intl」。它的做法是按国家 / 币种硬编码配置表（符号、精度、分隔符、符号位置）+ 服务端数字先放大换算（一般放大 1e5，IR 的 IRR 为 1e6）再格式化，compact 数字按国家 + 语言分表。原因按重要性排：

  • RN 的 Intl 历史不可靠——跨端要同一套结果，不能赌各端 ICU 实现
  • 跨端价格必须确定性一致——价格差一位都是事故，不能「差不多」
  • 主维度是国家、不是语言——同一语言多个国家的价格规则不同，Intl 的 locale 维度对不上
  • 自定义日期 pattern 超出 Intl 预设——业务要的格式，预设给不出来
  • ICU polyfill 体积——不适合低端机，包体积是真约束

收尾必加一句：纯 Web 新项目直接用 Intl 完全没问题，别把这套讲成「Intl 不好」——是多端 + 强一致的约束把平台层逼成了收敛自研，代价是新国家、新币种都要改配置发版。

Node 算跨端吗？先把两个词分开（高频陷阱题）

Node 是跨平台运行时，不是跨端 UI 框架。跨平台 = 同一份 JS 能在 Windows / macOS / Linux 上跑；跨端 = 同一份 UI 代码能在 iOS / Android / Web 上画出来。Node 不画 UI，所以严格说不算跨端，它是跨端体系的底座。

  • V8 屏蔽 CPU 架构：JS 不用管底层是 x86 还是 ARM
  • libuv 屏蔽操作系统：文件、网络、定时器统一成事件循环——Linux 用 epoll、macOS 用 kqueue、Windows 用 IOCP，阻塞 IO 丢线程池
  • 它在跨端的真实位置：Electron = Chromium + Node 做桌面跨端；RN 的打包器 Metro、DSL 编译、SSR / BFF 服务，全是 Node 在跑
  • 别说错：想在手机上直接跑 Node 画 UI 不现实，移动端还是要走 RN / Flutter 的渲染路线

长列表：FlatList 和 Web 虚拟列表是同一个思想

FlatList 窗口化怎么做

  • 只渲染窗口内 + 缓冲区的行，滚出窗口的行回收——和 Web 虚拟列表「DOM 数量与数据量解耦」完全同构，面试可以互相对照着讲
  • keyExtractor 给稳定业务 id，别用数组下标：数据增删时下标会错位、行会被错误复用
  • 行高固定时给 getItemLayout，跳过逐行测量、滚动定位可直接算
  • renderItem 别写内联闭包、行组件用 memo 包好——每次父组件重渲染都新建函数引用，行就跟着全量重渲染
  • 图片按行内展示尺寸给大小，别原图直塞小图位，既费流量又费解码和绘制

重渲染与性能坑：大多能归到两句话——过桥太频、JS 线程太忙

过桥的序列化成本

旧架构下大对象、大数组整包过桥，光序列化就吃时间。原则：过桥只传必要字段，大数据分页/分片传，高频事件（滚动、拖拽）别每帧过桥，动画走原生驱动（native driver / 把动画逻辑下发原生侧）。

JS 线程长任务

大计算、深拷贝、全量数据变换堵在 JS 线程上，渲染和事件全排队。打法：计算分片、重活延后到交互后（InteractionManager 等交互跑完再做）、能下沉原生的下沉，列表数据先在接口层减量再进 JS。

setState 风暴与无谓重渲染

高频 setState、父组件一变全树重渲染、内联对象/内联样式每次都是新引用——子组件 memo 全失效。对法：状态就近下沉、稳定引用（useCallback / useMemo 用在真有收益处，不是全加）、行与卡片组件 memo 化。Web React 的那套心法在 RN 原样成立。

为什么要「先解释、后 JIT」，不一上来就编译？

全量 AOT 编译启动慢，很多代码只跑一次、编译纯浪费。现代引擎的策略是分层：先用解释器快速启动，同时统计哪些函数是热点、参数实际是什么类型，只对热点做激进优化。代价是预热期性能不稳、类型多变的代码会反复去优化——这就是「别写类型乱变的对象、保持对象形状稳定（隐藏类 Hidden Class）」这条性能建议的根源。

三个必会的概念

  • 隐藏类：引擎按对象属性的添加顺序给对象分「形状」，同形状才能共享优化；到处动态加属性 = 形状爆炸
  • 内联缓存：把上次属性访问的结果缓存在调用点，类型不变就直接命中，变了就失效
  • GC：分代回收——新生代对象朝生夕死用复制算法，老年代用标记清除/整理；GC 暂停也是长任务和掉帧的一个来源，别在热路径疯狂造临时对象

三、CPU 与 GPU：为什么分工是这样分的

CPU · 少量强核，擅长串行与分支

  • 核心少（手机 4–8 核）、单核强、缓存大、擅长复杂逻辑和分支判断
  • 在前端链路里它干：JS 执行、样式计算、布局、绘制指令生成、图片解码的一部分
  • JS 主线程就在 CPU 的一个核上跑，所以一段长 JS 会同时堵住逻辑、布局和绘制——单线程的代价在这
  • 多核帮不上主线程：重计算要靠 Web Worker / 原生线程搬到别的核，但 Worker 不能直接碰 DOM

GPU · 海量弱核，擅长同一种计算重复百万次

  • 核心成千上万、单核弱、为并行而生：每个像素做同样的运算，正是它的主场
  • 在前端链路里它干：图层合成、光栅化、缩放旋转、透明度混合、图片缩放、视频解码、CSS 滤镜与 3D 变换
  • 它不跑你的 JS 业务逻辑：把逻辑丢给 GPU 不是选项，能丢的只有「画」这件事
  • 不是免费的：图层太多会爆显存、频繁把像素在 CPU 与 GPU 之间搬运（上传纹理）本身就贵，所以 will-change 滥用反而更慢

为什么 transform / opacity 是最便宜的动画？（必考）

因为它们只改合成阶段的参数：图层像素早就画好了，GPU 每帧只是把这张「贴纸」挪个位置、改个透明度，不需要重算布局、不需要重画。反过来动画里改 width / height / top / left，每一帧都要从 Layout 开始全链路重跑。RN 里动画要开 native driver、把动画下发原生侧，Web 里长列表要用 transform 定位，都是同一个道理的不同版本。

硬件加速的边界（别神化 GPU）

  • 合成线程独立是好事，但主线程堵死时，布局和绘制照样停，新内容画不出来，GPU 只能拼旧图层
  • 图层不是越多越好：每个图层占显存、合成时都要参与计算，移动端低端机先爆的是内存
  • 文字、复杂路径的绘制仍主要靠 CPU 生成，GPU 加速帮的是搬运和拼图，不是万能药
  • 答题落点：先定位卡在哪一阶段，再谈要不要上 GPU / Worker，别上来就说「开硬件加速」
一分钟讲法：

「我按一条链讲：JS 引擎在 CPU 上执行代码，它是解释加 JIT 分层编译——先解释快速启动、热点再编译成机器码，类型变了就去优化，所以对象形状要稳定；V8、JSC、Hermes 的区别主要在编译时机，Hermes 靠预编译字节码换 RN 的启动速度。渲染引擎接着干样式、布局、绘制、合成四步，Blink、WebKit、Gecko 是三家实现，Flutter 的 Skia 是自绘路线。CPU 和 GPU 的分工是：CPU 核少但强、管串行逻辑，所以 JS 和布局都在它身上；GPU 核多、管并行画像素，合成、缩放、透明度归它。所以动画只改 transform 和 opacity 最便宜，因为只动 GPU 合成、不惊动主线程的布局和绘制；卡顿定位也是先分清是 JS 长任务、回流、重绘还是合成出了问题，再对症下药。」

追问预警：「JS 是单线程，那 Worker 算多线程吗？」→ Worker 是另开一个 JS 线程在别的 CPU 核上跑，能算不能碰 DOM，结果靠消息传递回来，所以它治的是计算卡，不是渲染卡。「GPU 既然这么强，为什么不让它跑 JS？」→ GPU 为同指令大批量并行设计，JS 满是分支和依赖、数据量又小，搬过去光传输成本就亏了。「JIT 和 AOT 谁好？」→ 没有谁好：JIT 峰值高但要预热、占内存，AOT（Hermes / Dart）启动快、行为可预测但放弃了运行时激进优化——按场景选，这和第 29 节选渲染路线是同一种取舍思维。被追到引擎源码实现就收住：「我到原理层，隐藏类、内联缓存、去优化这些机制我能讲清，源码没读过。」
